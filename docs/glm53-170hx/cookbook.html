GLM-5.3-Flash on four CMP 170HX mining cards

A ~180 GB mixture-of-experts model serving up to its full 1M-token context on four ex-mining GPUs over PCIe Gen2 with no NVLink, at 90–165 tokens/s on short contexts and about 50 t/s deep in a 1M one. This page covers what it does, how it's configured, and how to launch it.

vLLM v0.30.0 fork · PP4 · DFlash2 speculative decoding · TurboQuant fp8 KV · 4× GA100 64 GB

Context and KV cache

The model's native limit is 1,048,576 tokens, and the rig runs it at the full 1M (see Long-context results). The benchmarks below were taken at a 262,144-token limit. How many full-length requests fit at once depends on how the KV cache is stored. Two changes raised it at 256k from 2.4 to 7.35:

TurboQuant fp8 KV

The sparse-attention layers store their 512-wide latent as one fp8 byte per value instead of two bf16 bytes, which halves attention cache pages. Ampere can't load e4m3 in Triton, so SM80 stores e5m2 and decodes with a bitcast. The fp8 reads are cheap enough that decode is no slower, and faster in some tests.

Private drafter pool

The DFlash drafter only needs a ~22.8k-token sliding window, but it had been using 89 block IDs per request from the same pool as the main model. It now has its own fixed 3.5 GB pool on the last card, which cut main-pool demand per 256k request from 151 blocks to 62.

The drafter pool is sized for max-num-seqs 8, so 7.35 is close to the ceiling for this config. Allowing more concurrent sequences would require a larger drafter reservation.

Growing conversation

An 11-turn session grew by 45k tokens per turn to 496k. Every turn recalled both the newest fact and one from the first turn, with no looping or degraded output.

Every turn re-reads the whole conversation. Prefix caching is off in this configuration, so a follow-up turn waits as long as the first: about 1 minute at 256k, 2 at 512k, 4.6 at 1M. The 11-turn session spent 11.3 minutes in prefill, where reading only the new text would take about 2. Prefix caching for this layout is in progress.

Launch recipe

This requires our patched vLLM branch; stock vLLM v0.30.0 won't run this model on SM80. The environment variables matter as much as the flags.

# --- environment ---
export CUDA_DEVICE_ORDER=PCI_BUS_ID
export CUDA_VISIBLE_DEVICES=0,1,2,3
export NCCL_P2P_DISABLE=1              # no usable P2P on these cards
export NCCL_IB_DISABLE=1
export VLLM_WORKER_MULTIPROC_METHOD=spawn
export VLLM_PP_LAYER_PARTITION=13,12,11,9   # layers per card; card 0 caps at 13
export VLLM_GLM5N_SIDECAR_BLOCK_SIZE=256    # drafter KV block size
export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False
export HF_HUB_OFFLINE=1

# --- server ---
python -m vllm.entrypoints.openai.api_server \
  --model /models/GLM-5.3-Flash-AWQ-W4A16 \
  --served-model-name glm53-flash \
  --pipeline-parallel-size 4 \
  --max-model-len 262144 \
  --max-num-seqs 8 \
  --max-num-batched-tokens 4096 \
  --gpu-memory-utilization 0.93 \
  --kv-cache-dtype turboquant_k8v4 \
  --no-enable-prefix-caching \
  --disable-custom-all-reduce \
  --speculative-config '{"method":"dflash","model":"/models/GLM-5.3-Flash-DFlash2","num_speculative_tokens":7,"kv_cache_dtype":"auto"}' \
  --enable-auto-tool-choice --tool-call-parser glm47 \
  --reasoning-parser glm45 \
  --host 0.0.0.0 --port 8002

Cold start takes about 4 minutes, mostly weight load, repacking and CUDA-graph capture. On the first boot, Triton kernel compilation adds several more minutes.

Why these settings

--max-model-len262144 is the benchmarked setting. 1048576 enables the full 1M context and still serves short requests; its throughput under many concurrent mid-size requests hasn't been benchmarked.
--kv-cache-dtype turboquant_k8v4fp8 attention cache. Remove it for bf16 KV at about 26% fewer cache tokens.
"kv_cache_dtype":"auto" in the drafter configRequired. No backend runs the drafter's sliding-window attention on a TurboQuant cache, so the drafter stays on bf16.
--gpu-memory-utilization 0.93The tested ceiling. 0.95 caused faults.
Partition 13,12,11,9Card 0 faults when loading more than 13 MoE layers. Layers 0–2 have dense MLPs, so card 0 carries less weight than its layer count suggests, and card 1 ends up the tightest.
--disable-custom-all-reduceThe custom all-reduce's BAR1 mappings triggered copy-engine faults on these cards.
--no-enable-prefix-cachingRequired by the private drafter pool and the hybrid KV layout.
--max-num-seqs 8Sets the drafter pool size (8 × 89 blocks). Raising it grows that reservation on the last card.

Using it

The server exposes an OpenAI-compatible API. The model always reasons; the reasoning comes back in a separate field.

curl http://HOST:8002/v1/chat/completions -H 'Content-Type: application/json' -d '{
  "model": "glm53-flash",
  "messages": [{"role": "user", "content": "What is 17 plus 25?"}],
  "temperature": 0,
  "max_tokens": 4096,
  "include_reasoning": false
}'
Don't send enable_thinking: false. This checkpoint's chat template ignores it and still starts a reasoning block, but the parser stops separating reasoning from the answer, so you get outputs like 17 + 25 = 4242. Use "include_reasoning": false to hide the reasoning. The model still generates it and you still pay for those tokens.
  • Leave room for reasoning in max_tokens. On hard review questions the model can reason for 20k+ tokens before it answers.
  • Tool calling works through the glm47 parser with the standard OpenAI tools field.

Operating notes for these cards

  • Stop with SIGTERM, never SIGKILL. Killing a worker while it scrubs VRAM can wedge the GPU firmware, and only a reboot recovers it.
  • Wait before restarting. After the API server exits, workers can hold VRAM for several more minutes. Relaunch only when nvidia-smi shows no compute processes and the port is free.
  • One CUDA workload at a time. Running anything else on the GPUs while serving, even a quick test, risks the same firmware wedge.
  • Pin the kernel. The unlocked driver is built for one kernel version, and a kernel update makes the GPUs disappear.
  • After a GPU fault (Xid 31), a full driver-module reload usually clears it. nvidia-smi --gpu-reset does not.

What's next

Prefix caching

Reuse the previous turn's cache so a follow-up in a long session only reads its new text. This is the biggest remaining win for long, many-turn projects.

3-bit TurboQuant

Rotated, codebook-quantized KV at about 5× compression versus bf16. The kernels are already ported; the next step is validating quality. Expect some decode cost in exchange for more context.

Partition retune

Card 1 is the tightest because it carries the most expert weight. Shifting a layer, for example to 14/11/11/9, could free more cache.
